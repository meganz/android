# CLAUDE.md

This file provides guidance to Claude Code when working in the `:core:analytics:analytics-tracker` module.

> Module path: `:core:analytics:analytics-tracker` · Build file: `core/analytics/analytics-tracker/analytics-tracker.gradle.kts` · Namespace: `mega.privacy.android.analytics`

## Overview
This module is the app-side abstraction for emitting analytics events. It wraps the MEGA Mobile Analytics SDK (`mega.privacy.mobile.analytics`) behind a small `AnalyticsTracker` interface and exposes a process-wide `Analytics` singleton so any layer (presentation, navigation, etc.) can track events without holding a Hilt-injected dependency.

It also bridges navigation and Firebase: a Navigation3 `NavEntryDecorator` automatically tracks screen-view and dialog-displayed events from nav entry metadata, and mirrors screen views into Firebase Analytics so crashes can be associated with the current screen.

## Architecture & Layout
- `mega.privacy.android.analytics` (root): the `Analytics` singleton entry point, plus the SDK contract implementations `EventSenderImpl` and `ViewIdProviderImpl`.
- `…analytics.tracker`: the `AnalyticsTracker` interface and `AnalyticsTrackerImpl`.
- `…analytics.di`: Hilt wiring (`AnalyticsModule`) and the `AnalyticsEntrypoint` used by the `Analytics` singleton to resolve the tracker from the application context.
- `…analytics.decorator`: the `AnalyticNavEntryDecorator` and metadata helpers for navigation-driven event tracking.

## Key Components
- `AnalyticsTracker` / `AnalyticsTrackerImpl` — interface with `trackEvent(EventIdentifier)`; the impl delegates to the SDK `Tracker`.
- `Analytics` — `object` singleton initialised from a `Context` (via `AnalyticsEntrypoint`) or directly with a tracker (e.g. for tests); exposes `Analytics.tracker`.
- `EventSenderImpl` — SDK `EventSender`; forwards events to `SendUserJourneyEventUseCase` on the `@ApplicationScope` coroutine scope.
- `ViewIdProviderImpl` — SDK `ViewIdProvider`; supplies the current view id via `GetViewIdUseCase`.
- `AnalyticNavEntryDecorator` — Navigation3 decorator that tracks `ScreenViewEventIdentifier` / `DialogDisplayedEventIdentifier` from nav entry metadata and logs Firebase `SCREEN_VIEW`. Use `NavEntryMetadataScope.withScreenViewEvent(...)` / `withDialogEvent(...)` to attach events, and `rememberAnalyticNavEntryDecorator()` to obtain it.
- `AnalyticsModule` — binds `AnalyticsTrackerImpl` and provides the SDK `Tracker` (wiring `ViewIdProviderImpl`, `EventSenderImpl`, `AppIdentifier(0)`).

## Module Dependencies
- `:domain` — use cases (`SendUserJourneyEventUseCase`, `GetViewIdUseCase`) and `@ApplicationScope`.
- `:core:navigation-contract` — `NavEntryMetadataScope` for nav metadata.
- `:lint` — lint checks.
- External: MEGA Mobile Analytics SDK (`lib.mega.analytics`), Firebase Analytics (`google.firebase.bom`), AndroidX Navigation3 runtime + Compose, `javax.inject`, Timber logging.

## Testing

`./gradlew core:analytics:analytics-tracker:testDebugUnitTest`

## Notes & Gotchas
- Events are defined as SDK `EventIdentifier` types (e.g. `ScreenViewEventIdentifier`, `DialogDisplayedEventIdentifier`), typically code-generated by the analytics SDK — do not hand-author event identifiers here.
- `Analytics.tracker` throws `IllegalStateException` if accessed before `Analytics.initialise(...)`; initialise early in app startup.
- `AnalyticNavEntryDecorator` reads the private `NavEntry.key` field via reflection to derive the Firebase screen name. NavKey classes are `@Serializable` and ProGuard keeps their names, so `simpleName` stays correct in release builds — preserve that ProGuard rule.
- `onPop` is currently a no-op; the decorator only tracks on display.
- See root `.claude/CLAUDE.md` for global Clean Architecture, Hilt, and testing conventions.
